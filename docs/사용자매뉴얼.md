# SRMS 사용자 매뉴얼 (롤별)

시스템 유지보수 요청 관리(SRMS)를 롤별로 어떻게 쓰는지 설명합니다. 자기 롤의 장과 §1(공통)을 읽으면 됩니다. 화면 문구는 한국어 기준이며 일본어·영어·중국어로 바꿔 쓸 수 있습니다. 교육용 롤별 PowerPoint(화면 캡처 포함)는 [ppt/](ppt/) 폴더에 있습니다.

| 내 역할 | 읽을 장 |
|---|---|
| 유지보수를 요청하는 현업 담당자 | §1, §2 |
| 현업 부서의 전산 담당자(승인 담당) | §1, §2, §3 |
| 전산팀(검토·수행·종료, 팀장 포함) | §1, §2, §4 |
| 시스템관리자 | §1, §5 |

한 사람이 여러 롤을 가질 수 있습니다. 그런 경우 해당 롤의 장을 모두 보세요.

---

## 1. 공통

### 1.1 로그인과 기본 화면

1. 접속 주소를 열고 **회사**, **로그인 ID**, **비밀번호**를 입력해 `로그인` 합니다. 단일 회사로 설치된 서버에서는 회사 선택이 나타나지 않습니다. 사내 SSO 가 연결된 서버에는 `사내 SSO 로그인` 버튼이 있습니다.
2. 비밀번호를 5회 틀리면 계정이 15분간 잠깁니다. 잠시 뒤 다시 시도하거나 관리자에게 재설정을 요청하세요(관리자가 비밀번호를 재설정하면 잠금 중에도 바로 로그인할 수 있습니다).
3. 일정 시간(기본 30분) 사용하지 않으면 자동으로 로그아웃됩니다. 다시 로그인하세요.

상단 메뉴는 권한에 따라 다르게 보입니다.

| 메뉴 | 보이는 사람 |
|---|---|
| 홈(대시보드) | 모두 |
| 요청 등록 | 요청을 등록할 수 있는 모든 롤 |
| 요청 목록 | 모두 |
| 처리함 | 단계를 처리할 수 있는 롤 |
| 작업일지 | `작업일지 등록·관리` 권한이 있는 롤(기본: 전산팀, 시스템관리자) |
| 리포트 | 현업 전산담당, 전산팀, 시스템관리자 |
| 관리(사용자/부서/롤/공통코드/서비스/프로세스 관리/서비스×타입 매핑/메일 템플릿/메일 발송 이력) | 시스템관리자 |

상단 오른쪽에는 **테마(밝은/어두운)** 전환, **언어** 선택, **내 이름 메뉴**(내 정보, 로그아웃)가 있습니다.

### 1.2 내 정보

`내 이름 > 내 정보`에서 이름, 이메일, 사용 언어를 바꾸고 **비밀번호를 변경**합니다. 비밀번호는 8자 이상이며 영문과 숫자를 모두 포함해야 하고 로그인 ID 와 같으면 안 됩니다. 이메일이 틀리면 알림 메일을 받을 수 없으니 정확히 입력하세요. 메일은 내가 선택한 언어로 옵니다.

### 1.3 테마와 언어

- **테마**: 오른쪽 위의 `어두운 테마`/`밝은 테마` 버튼으로 바꿉니다. 내 계정에 저장되어 다른 PC에서도 유지됩니다.
- **언어**: 오른쪽 위 언어 메뉴에서 선택합니다. 요청 제목·본문·의견처럼 사람이 입력한 내용은 번역되지 않고 입력한 그대로 보입니다.

### 1.4 요청의 상태

| 상태 | 의미 |
|---|---|
| 임시저장 | 요청자가 작성 중이며 제출 전. 요청자만 볼 수 있습니다 |
| 진행중 | 제출되어 프로세스 단계를 따라 처리 중 |
| 보완요청 | 반려되어 요청자가 내용을 고쳐 다시 제출해야 하는 상태 |
| 완료 | 마지막 단계(종료)까지 끝남 |
| 취소 | 요청자가 취소함 |

**지연** 배지는 완료요구일을 넘긴 진행 건(또는 완료요구일보다 늦게 끝난 완료 건)에 붙습니다(목록과 상세 화면 모두 `지연 N일`). 목록에서는 진행 중인 지연 건의 행 전체가 옅은 빨간 배경으로 표시됩니다. **일정 협의 중** 배지는 일정 변경 협의가 끝나기 전까지 그 요청의 단계 처리가 멈춰 있다는 뜻입니다. **작업일지** 배지는 전산팀이 사후에 기록한 완료 건, **분할** 배지는 SR 분할로 나뉜 요청(원본·새 SR 모두)입니다.

### 1.5 요청 상세 화면 읽는 법

- 맨 위 **프로세스 흐름**: 단계가 가로로 늘어서 있고 완료(초록)/진행중(파랑, 굵은 테두리)/대기를 보여 줍니다. 각 단계에는 처리자와 기한이 표시됩니다.
- 왼쪽: 처리 영역(내 차례일 때만), 일정 협의, 내용, 첨부파일(단계별), 진행 이력(결재·반려·일정 변경·댓글·첨부가 시간순으로 통합되고 반려 사유 포함), 댓글 입력.
- 오른쪽 요약: 서비스, 유지보수 타입, 우선순위, 요청자, **완료요구일**, **합의 완료일(계획)**, 실제 완료일, 투입시간, 적용 프로세스와 버전, 등록일.
- 요청에 적용되는 프로세스는 **제출하는 시점의 버전으로 고정**됩니다. 나중에 관리자가 프로세스를 바꿔도 진행 중인 요청은 영향을 받지 않습니다.
- 내가 처리자가 아닌 진행 중 요청을 열면 상단에 `현재 "수행" 단계는 ○○ 님이 처리합니다` 안내가 나오며 처리 버튼은 보이지 않습니다. 단계마다 처리자가 다릅니다(검토·종료는 전산팀 롤 전원, 승인은 서비스에 지정된 현업 IT 담당자(지정이 없으면 주관부서의 현업 전산담당), 수행은 서비스에 지정된 전산 담당자 한 명, 검수는 요청자).

### 1.6 메일 알림 규칙

메일은 **내가 무언가를 해야 할 때만** 옵니다. 진행 결과만 궁금하면 메일 대신 화면(홈, 요청 상세)에서 확인합니다.

| 상황 | 메일을 받는 사람 |
|---|---|
| 내 차례가 된 단계(제출, 이전 단계 승인) | 해당 단계의 처리자 |
| 반려 또는 보완요청 | 다시 처리해야 하는 사람(이전 단계 처리자 또는 요청자) |
| 일정 변경 요청 | 요청자(합의 여부 회신) |
| 일정 변경 반려/대안 제시 | 요청한 작업자 |
| SR 분할 | 요청자(분할 안내), 새 SR 현재 단계 처리자 |
| 기한 임박/초과 | 아직 처리하지 않은 현재 단계 처리자 |
| 참조자 설정이 된 단계 | 참조자(관리자가 설정한 경우에만, 처리 버튼 없는 안내 메일) |

자기가 직접 한 처리에 대해서는 메일이 오지 않습니다. 일정 변경에 **합의**했을 때는 메일이 없습니다. 작업일지 등록에도 메일이 없습니다.

기한 독촉 메일은 주기 작업(`bin/cron.php`)이 **단계의 표준 기한**이 다가왔거나(기본 1영업일 전) 지난 단계에 대해 보냅니다. 같은 건은 중복 발송하지 않고, 일정 변경 협의 중인 요청은 제외합니다. 홈의 **기한 임박**(유효 완료일이 오늘부터 3일 이내)과는 기준이 다릅니다.

### 1.7 요청 목록 사용법

- 탭: `내 요청`, `처리함`(내가 처리할 건), `주관부서`(내 부서가 주관하는 서비스 요청, 현업 전산담당), `전체`(관리 범위 전체, 전산팀·시스템관리자), `참조`(참조자로 지정된 건). 권한이 없는 탭은 보이지 않습니다. 임시저장 건은 요청자 본인에게만 보입니다.
- 상태, 서비스, 번호/제목 검색으로 좁힙니다. 조건에 맞는 건이 없으면 표 안에 `조건 초기화` 링크가 나옵니다.
- 표 열 순서는 `요청번호 · 상태 · 제목 · 현재 단계 · 서비스 · 유지보수 타입 · 요청자 · 완료요구일 · 최종 변경`입니다. 제목이 길면 뒤를 줄여 표시하고 마우스를 올리면 전체 제목이 보입니다.
- 건수가 많으면 아래에 `1–20 / 총 85건` 형식의 범위와 `이전`/`다음`, 현재 페이지 주변 번호가 나옵니다. 페이지를 옮겨도 선택한 탭과 검색 조건이 유지됩니다. 한 페이지 건수는 서버 담당자가 `.env` 의 `LIST_PAGE_SIZE`(기본 20, 5~200)로 정합니다. 메일 발송 이력은 `MAIL_LOG_PAGE_SIZE`(기본 30)입니다.
- 열람 권한이 없는 요청 주소를 직접 열면 존재 여부를 숨기기 위해 `404` 화면이 나옵니다.

## 2. 현업 사용자 (REQUESTER)

유지보수를 요청하고, 내 요청이 어디까지 진행됐는지 확인하는 역할입니다. 기본 권한: 요청 등록, 본인 건 조회, 참조 지정된 건 조회, 단계 처리(내가 처리자인 단계), 일정 변경 회신.

### 2.1 홈(대시보드)에서 볼 것

- **내 요청 현황**: 상태별 건수.
- **내 조치 대기**: `처리 필요`(내가 처리할 단계), `보완 필요`(반려된 내 요청), `일정 협의 회신`(작업자가 일정 변경을 제안한 건).
- **진행 중인 내 요청**: 단계 진행률(예: 6단계 중 3단계 완료).
- **최근 알림**: 내게 발송된 최근 메일 알림 5건(제목·시각, 누르면 해당 요청으로 이동). 내 차례가 된 단계, 반려, 일정 변경 제안, 분할 안내, 기한 독촉 등이 쌓이며, 받은 알림이 없으면 `표시할 항목이 없습니다.` 가 나옵니다.

### 2.2 요청 등록

1. 상단 `요청 등록`을 누릅니다.
2. **서비스**와 **유지보수 타입**(신규개발, 기능수정, 장애처리, 데이터작업, 기타)을 선택합니다. 선택하면 이 요청에 적용될 **프로세스 흐름이 미리 표시**됩니다. 이 조합에 프로세스가 연결되어 있지 않으면 등록할 수 없으니 관리자에게 문의합니다.
3. **제목**(200자 이하), **우선순위**, **완료요구일**(필수, 오늘 이후), **내용**을 입력합니다. 완료요구일은 약속된 완료 일정이며 나중에 작업자가 맞출 수 없을 때 협의의 기준이 됩니다. 내용은 편집기에서 서식을 넣을 수 있습니다.
4. **첨부파일**을 추가합니다(여러 개 한 번에 선택 가능). 선택한 파일의 이름·크기·합계가 입력칸 아래에 목록으로 표시되고, 파일 옆의 `×` 를 누르면 그 파일만 선택에서 뺀 수 있습니다. 파일당 기본 최대 20MB, 허용 확장자만 가능하며 실행 파일은 올릴 수 없습니다.
5. `임시저장`으로 나중에 이어서 쓰거나, `제출`로 프로세스를 시작합니다. 제출하려면 제목과 내용이 있어야 합니다.

제출하면 첫 처리 단계의 처리자에게 메일이 갑니다. 요청번호(`SR-연월-일련번호`)는 처음 저장할 때(임시저장 포함) 부여됩니다.

### 2.3 내 요청 확인

- `요청 목록`의 탭에서 `내 요청`을 봅니다. 상태, 서비스, 번호/제목으로 검색할 수 있습니다.
- 목록에서 번호를 누르면 상세 화면이 열립니다. 현재 어느 단계에 누가 처리 중이고 기한이 언제인지는 **프로세스 흐름**에서 한눈에 볼 수 있습니다.
- 질문이나 추가 설명은 상세 화면 아래 `댓글`로 남깁니다.
- 요청 하나에 IT 담당자가 둘 필요하면 전산팀이 요청을 **분할**합니다. 이 경우 안내 메일이 오고 상세 화면에 `분할된 SR`/`분할 원본` 링크가 생깁니다. 각 SR 은 담당자·일정·완료가 따로 진행되고, 모두 내 요청에서 확인하고 각각 검수합니다.
- 전산팀이 전화·메일·메신저로 받은 요청을 사후에 기록한 **작업일지**도 `내 요청`에 완료 건으로 나타납니다(`작업일지` 배지). 요청자는 내용·첨부를 보고 댓글만 남길 수 있으며 수정·취소·검수는 없습니다.

### 2.4 반려(보완요청)를 받았을 때

1. `보완요청` 상태가 되고 상세 화면 위에 **반려 사유**가 표시됩니다.
2. `수정`을 눌러 내용을 고치고 필요하면 첨부를 바꾼 뒤 `보완 후 재제출`을 누릅니다. 프로세스는 첫 처리 단계부터 다시 진행됩니다.
3. 더 이상 진행하지 않을 때는 `요청 취소`를 누릅니다.

### 2.5 내가 처리자인 단계(요청자 단계)

기본 프로세스에서 **검수** 단계는 요청자가 처리합니다. 결과물을 확인한 뒤 의견을 적고 `검수 승인`을 누릅니다. 수정이 더 필요하면 `반려`(사유 필수)를 누르면 작업 단계로 돌아갑니다. 이 단계에서 첨부가 필수로 설정되어 있으면 파일을 먼저 올려야 처리됩니다.

### 2.6 일정 변경 회신(완료요구일 협의)

작업자가 완료요구일을 맞출 수 없으면 **가능한 완료일과 사유**를 제안하고, 요청자에게 메일이 갑니다. 이때 요청 상세에 `일정 변경 협의 대기 중` 안내가 나타납니다.

| 선택 | 결과 |
|---|---|
| `합의` | 변경된 완료일이 **합의 완료일(계획)** 로 확정됩니다 |
| `반려` | 기존 완료요구일이 유지됩니다. 의견 필수 |
| `대안 제시` | 내가 원하는 완료일(오늘 이후이면서 제안일보다 앞)과 의견을 보내 다시 협의합니다 |

- 회신 기한은 기본 3영업일이며 지나면 독촉 메일이 매일 옵니다.
- 합의 전까지 **그 요청의 단계 처리는 중단**됩니다.
- 변경 이력(어느 단계에서, 누가, 어떤 사유로, 누가 동의했는지)은 상세 화면의 `일정 변경 이력`과 진행 이력에 남습니다.
- 일정 변경 합의는 **요청자 본인만** 할 수 있고, 요청자는 일정 변경을 제안하지 않습니다.

### 2.7 요청 취소

`임시저장`, `진행중`, `보완요청` 상태의 요청은 요청자가 `요청 취소`로 취소할 수 있습니다. 완료된 요청은 취소할 수 없습니다. 취소해도 이력은 삭제되지 않습니다.

## 3. 현업 전산담당 (BIZ_IT)

현업 부서에 소속된 IT 담당자입니다. **현업 사용자 권한에 더해** 주관부서 요청을 보고, 승인 단계를 처리하고, 리포트를 볼 수 있습니다.

### 3.1 홈(대시보드)

현업 사용자 화면에 **주관부서 현황**이 추가됩니다(내 부서가 주관하는 서비스의 요청만).

- 단계별 진행 건수, 지연, 기한 임박, 일정 협의 중, 신규 접수.
- 내 조치 대기(내가 승인해야 할 건 포함).

내 소속 부서가 지정되어 있지 않으면 주관부서 현황이 나오지 않으니 관리자에게 부서 지정을 요청하세요.

### 3.2 요청 목록과 처리함

- `요청 목록`에 `내 요청`과 함께 `처리함`, `주관부서`, `참조` 탭이 있습니다. `주관부서`는 내 부서가 주관하는 서비스의 요청 전체입니다.
- 상단 `처리함`에는 내가 지금 처리해야 하는 요청이 모입니다.
- `주관부서` 탭에는 내 부서 서비스의 작업일지도 `작업일지` 배지와 함께 보입니다(`작업일지` 메뉴와 등록 화면은 없습니다).

### 3.3 승인 단계 처리

기본 프로세스에서 **승인**(긴급 프로세스는 **사후합의**) 단계는 해당 서비스에 지정된 **현업 IT 담당자**가 처리합니다(주관부서 소속의 현업 전산담당 중에서 관리자가 지정, 지정이 없거나 지정자가 모두 자격을 잃으면 그 부서의 현업 전산담당 전원). 전산팀 검토를 마친 뒤 내 차례가 되며 메일이 옵니다. 단계 설정에 따라 한 명이 처리하면 끝나거나(`1명 처리 시 완료`) 전원이 처리해야 합니다(`전원 처리 시 완료`).

1. 처리함에서 요청을 열어 범위와 일정이 현업 요구와 맞는지 확인합니다.
2. 의견을 적고 `승인`을 누릅니다. 문제가 있으면 의견(필수)을 적고 `반려`를 누릅니다. 반려하면 프로세스에 정해진 이전 단계(기본: 검토)로 돌아갑니다.

한 번 처리하면 같은 회차에서 다시 처리할 수 없습니다.

### 3.4 리포트

`리포트`에서 **주관부서 서비스의 실적만** 볼 수 있습니다(§4.5와 같은 화면, 범위만 다릅니다).

## 4. 전산팀 (IT_TEAM)

유지보수를 검토하고 수행하는 팀입니다(팀장 포함). 현업 전산담당 권한에 더해 **관리 범위 전체 요청**을 봅니다.

### 4.1 홈(대시보드)

**전산팀 전체 현황**이 표시됩니다.

- **단계별 진행 보드**(칸반): 단계마다 진행 중인 요청 카드.
- **담당자별 부하**: 담당자별 진행 건수(요청 담당자가 없으면 서비스 전산 담당자 기준). 담당자가 없으면 `미지정`.
- **서비스별 진행 건수**, **신규 접수**, **지연**, **기한 임박**(유효 완료일이 오늘부터 3일 이내), **일정 협의 중**.
- 내 조치 대기.

`요청 목록`의 `전체` 탭은 관리 범위 전체 요청(임시저장 제외)입니다. 홈에는 소속 부서가 주관하는 서비스가 없어도 `주관부서 현황` 블록이 함께 보일 수 있으며(0건), 전산팀 전체 현황과 별개입니다.

### 4.2 처리함에서 단계 처리

기본 프로세스(일반)의 단계별 처리자는 다음과 같습니다. 전산팀이 하는 일은 검토, 수행(서비스 전산 담당자인 경우), 종료입니다.

| 단계 | 처리자 | 하는 일 | 반려하면 |
|---|---|---|---|
| 검토 | 전산팀 롤 | 요청 내용이 타당한지, 접수 가능한지 판단하고 `검토 완료` | 요청자에게 반환(보완요청) |
| 승인 | 서비스 현업 IT 담당자(미지정 시 주관부서의 현업 전산담당) | (현업 전산담당 §3.3) | 검토로 이동 |
| 수행 | 해당 서비스의 **전산 담당자** | 실제 작업. 완료 후 `작업 완료`. 투입시간 입력 | 반려 불가 |
| 검수 | 요청자 | (요청자 §2.5) | 수행으로 이동 |
| 종료 | 전산팀 롤 | 결과 확인 후 `종료` | 반려 불가 |

긴급 프로세스(`긴급 장애`)는 접수 → 승인 → 수행 → 사후합의 → 종료로 짧습니다.

처리 방법: 처리함 또는 요청 목록에서 요청을 열고, 처리 카드에 의견을 적은 뒤 단계 버튼(예: `검토 완료`, `작업 완료`, `종료`) 또는 `반려`를 누릅니다. 반려에는 사유가 필수입니다. 첨부가 **필수**인 단계는 파일을 먼저 올려야 처리됩니다. 첨부는 상세 화면 `첨부파일` 영역에서 올립니다. 단계 설정은 요청을 접수한 시점의 프로세스 버전을 따르므로, 이전 버전에서 시작한 요청에는 새 버전의 첨부 필수 설정이 적용되지 않습니다.

> 수행 단계는 롤이 아니라 **서비스에 지정된 전산 담당자**(또는 전산팀이 그 요청에 따로 지정한 담당자, 4.7)가 처리합니다. 서비스에 전산 담당자가 지정되지 않았거나 다른 사람이면 처리할 수 없으니, 관리자에게 서비스 담당자 지정을 요청하세요.

### 4.3 투입시간 입력

수행(작업) 단계의 처리자는 진행 중이거나 완료된 요청의 상세 화면 오른쪽 `투입시간`에 **시간** 단위로 숫자(예: `2`, `0.25` = 15분, 소수 둘째 자리까지, 0~9999.99)를 입력해 저장합니다. 입력한 시간이 그대로 저장되고 상세에는 `9.5시간` 처럼 표시됩니다. 이 값이 리포트의 투입시간 집계(소수 둘째 자리)에 쓰입니다. MD(인일)로 환산해 저장하지 않으므로 하루 업무 시간 기준이 바뀌어도 입력한 시간은 그대로 남습니다.

### 4.4 일정 변경 요청(작업자)

완료요구일을 맞출 수 없을 때 **현재 단계의 처리자**(보통 수행 단계 담당자)가 요청 상세의 `일정 변경 요청`을 씁니다.

1. **가능한 완료일**(현재 유효한 완료일보다 늦어야 함), **사유**(요구범위 변경, 현업 요청, 선행 작업 지연, 리소스 부족, 기술 이슈, 테스트 이슈, 기타), **상세 사유**를 입력하고 `제안하기`를 누릅니다.
2. 요청자에게 메일이 가고, 합의 전까지 이 요청의 단계 처리가 중단됩니다.
3. 요청자가 반려하거나 대안을 내면 메일이 오고 기존 완료요구일이 유지됩니다. 필요하면 다시 제안합니다.
4. 제안을 거둘 때는 `요청 철회`를 누릅니다(제안한 본인만 가능).

한 요청에 협의는 동시에 1건만 열 수 있습니다. 합의 없이 방치하면 자동 조치 없이 **지연 실적**으로 집계됩니다.

### 4.5 리포트

`리포트`는 전산팀에서 **전체 서비스**를 대상으로 합니다.

- **화면 구성**: 위쪽 탭으로 `월간 현황`(기본)과 `상세 실적`을 바꿉니다. 탭마다 필요한 조건만 보이고, 조건 바로 아래에 **적용 조건**(연도·기간·서비스·타입·담당자)이 요약되고, 그 아래 한 줄 요약(예: `요청일 기준 · 임시저장·취소 건 제외 · 지연은 완료요구일 대비`)을 눌러 `기준 자세히 보기`로 정의를 펼칠 수 있습니다. 탭을 옮겨도 서비스·타입·담당자 조건은 유지됩니다.
- **상세 실적 탭의 필터**: 시작일, 종료일, 추이 표 단위(월/분기/연; 기간별 추이와 서비스×기간 표에만 적용), 서비스, 타입, 담당자. 기준은 **요청일**이며(일반 요청은 처음 제출한 날, 작업일지는 입력한 요청일, 보완 후 다시 제출해도 바뀌지 않음) 임시저장과 취소 건은 제외됩니다. 분할로 만든 새 SR 은 원본의 요청일을 그대로 이어받습니다.
- **월간 현황 탭**: `연도`를 고르면 1~12월을 가로로, **SR / 작업일지 / 전체**를 각각 세로로 보여 줍니다(시작일·종료일·추이 표 단위와는 무관하고 서비스·타입·담당자 필터는 적용됩니다). **SR 블록**의 행은 이월, 접수, 완료, 취소, 진행(기말), 기한 초과(합의 연장 중), 지연 완료, 완료율, 평균 처리일수, 투입시간(h)이고, **작업일지·전체 블록은 접수와 투입시간(h)만** 나옵니다(전체 = SR + 작업일지). 작업일지는 저장 즉시 정시 완료되므로 이월·완료율·지연 같은 지표는 SR 블록에서만 의미가 있고, 그래서 SR 서비스 수준이 작업일지 때문에 좋아 보이지 않습니다. 마지막에 접수·투입시간의 **SR·작업일지 비중(%)** 이 나오고, 위쪽 차트는 SR의 월별 접수·완료입니다.
  - 접수는 **요청일**, 완료는 **완료일**, 취소는 **취소일**이 속한 달에 셉니다. 접수에는 나중에 취소된 건도 포함되고 `취소` 행에 따로 나옵니다(제출하지 않고 취소한 건과 임시저장은 제외). 아직 오지 않은 달은 `-` 입니다.
  - `이월 + 접수 - 완료 - 취소 = 진행(기말)`이고, 진행(기말)은 다음 달의 이월과 같습니다. `완료율` = 완료 ÷ (이월 + 접수 - 취소), `평균 처리일수` = 그 달에 완료된 건의 요청일부터 완료일까지입니다.
  - `기한 초과`는 그 달 말일(이번 달은 오늘)에 아직 진행 중이면서 완료요구일이 지난 건, `지연 완료`는 그 달에 완료했지만 완료요구일을 넘긴 건입니다. 데이터를 별도로 확정(마감)하지 않고 현재 값으로 계산하므로, 지난 달 값도 데이터가 바뀌면 달라질 수 있습니다.
- **상세 실적 탭의 표와 차트**: 서비스별 실적, 담당자별 실적, 타입별 실적, 교차 집계(서비스×타입, 담당자×타입), 일정 준수/지연 실적(서비스별·담당자별), 일정 변경 사유별 분포, 프로세스 병목(단계별 평균 체류일), 기간별 추이.
- 건수, 완료, 진행중, 완료율, 평균 처리일수, 투입시간(h), 지연 건수 등이 나옵니다. 지연은 **완료요구일 대비**이며, 합의로 연장된 기한 안에 끝난 건은 따로 표시됩니다.
- 각 표의 `CSV` 내려받기를 누르면 엑셀에서 바로 열 수 있습니다(UTF-8).
- **표 보는 법**: 모든 표는 세로선이 있고 열 제목이 가운데 정렬됩니다. 지연·기한 초과 열은 값이 0보다 크면 빨간 글씨로 나오고, 합계 열은 굵은 글씨와 배경색으로 구분됩니다. `월간 현황` 표는 표 안에 세로 스크롤 없이 전체가 한 번에 보이고(화면이 좁아 가로로 스크롤할 때는 앞 두 열(구분, 지표)이 고정됩니다), SR/작업일지/전체/비중 그룹 사이에 굵은 선이 있으며 접수·완료·진행(기말) 행이 굵게 나옵니다. `상세 실적` 탭 위에는 표 이름 버튼(서비스별 · 담당자별 …)이 있어 눌러 해당 표로 이동하고, 넓은 화면에서는 열이 적은 표의 차트가 표 옆에 나란히 나옵니다.

### 4.6 작업일지(사후등록)

현업이 요청을 등록하지 않고 전화·메일·메신저로 연락해 왔을 때, 전산 담당자가 처리 후에 기록합니다(`작업일지` 메뉴, `WORKLOG_REG` 권한).

1. `작업일지 > 작업일지 등록` 에서 **요청일**(오늘 이전), **요청자**(등록된 사용자), **서비스**, 접수 채널(선택), 제목, 내용, **투입시간(시간, 0.01~9999.99)**, **완료일**(요청일 이후~오늘), 첨부를 입력합니다.
2. 저장하면 **승인 없이 바로 완료**되고 알림 메일은 발송되지 않습니다. 요청자의 `내 요청`에 완료 건으로 보입니다.
3. `작업일지` 목록은 회사 전체 건이 보이며 기간·요청자·서비스·검색어로 좁힙니다. **수정·삭제는 등록한 본인과 시스템관리자만** 할 수 있습니다. 삭제하면 첨부파일과 이력도 함께 지워지고 복구할 수 없습니다.
4. 리포트에서는 유형 `기타작업` 으로 따로 볼 수 있고, 투입시간은 담당자별 실적에 합산됩니다. 기간 기준은 등록일이 아니라 입력한 요청일입니다.
5. 작업일지 상세에는 투입시간 입력, 일정 변경 요청, 요청 취소, SR 분할, IT 담당자 지정이 없습니다. 수정은 `작업일지` 목록의 `수정` 버튼으로만 합니다. 접수 채널(전화·메일·메신저·방문·기타)은 관리자가 공통코드에서 이름을 바꿀 수 있습니다.

### 4.7 IT 담당자 지정과 SR 분할

`요청 분할·담당자 지정`(`REQUEST_SPLIT`) 권한이 있는 사용자(기본: 전산팀, 시스템관리자)가 진행 중인 일반 요청에서 합니다.

**IT 담당자 지정**
- 요청 상세 오른쪽 `IT 담당자`에서 사용자를 고르고 `지정`을 누릅니다. `(서비스 담당자)` 를 고르면 서비스에 지정된 담당자로 되돌아갑니다.
- 지정하면 그 요청의 **수행 단계는 지정된 사람만** 처리하고(서비스 담당자는 처리할 수 없음), 처리함·메일·리포트 담당자 집계도 그 사람 기준이 됩니다. 지정된 사람이 현재 단계 처리자이면 처리 요청 메일이 갑니다.
- 지정된 사람이 퇴사·비활성이면 처리할 사람이 없으므로 다시 지정하세요.

**SR 분할** (요청 하나에 IT 담당자가 둘 필요할 때)
1. 요청 상세의 `SR 분할` 카드를 열고 새 SR 제목, **작업 범위·분할 사유**, **새 SR 담당자**를 입력합니다(원본 담당자를 바꿔야 하면 함께 선택).
2. `분할`을 누르면 원본은 그대로 진행되고, 같은 서비스·유형·요청자·완료요구일의 **새 SR** 이 현재 단계에서 이어 시작합니다. 새 SR 본문 맨 위에 분할 안내가 들어갑니다.
3. 한 번에 새 SR 한 건이 만들어집니다. 3건 이상이 필요하면 분할을 반복합니다.
4. 첨부파일·일정 협의 이력·투입시간은 복사되지 않습니다(첨부는 원본에서 확인). 요청자에게 분할 안내 메일이 가고, 두 SR 은 서로 링크되며 목록에 `분할` 배지가 표시됩니다.

분할할 수 있는 시점: 현재 단계가 **검토·합의·승인·수행**이고 일정 변경 협의 중이 아닐 때만입니다(접수·검수·종료 단계, 완료·임시저장·보완요청 건, 작업일지는 불가). 다른 서비스로 보내는 분할은 지원하지 않습니다. 분할된 SR 은 리포트에서 각각 1건으로 집계됩니다.

## 5. 시스템관리자 (SYS_ADMIN)

사용자, 롤, 공통코드, 서비스, 프로세스, 메일 설정을 관리합니다. 모든 설정은 **내 회사 안에서만** 적용됩니다. 상단 `관리` 메뉴에서 접근합니다. 관리 화면의 목록도 세로선이 있는 표이고, 열 제목은 가운데 정렬되며 마지막 열은 `관리`(수정·삭제 등 버튼)입니다.

> 처음 설치한 직후에는 아래 순서로 설정하면 요청 등록까지 갈 수 있습니다: 부서 → 사용자 → 서비스 → (필요 시) 공통코드/프로세스 → 서비스×타입 매핑 → 메일 확인. 자세한 현장 설치 순서는 [신규회사설치가이드.md](신규회사설치가이드.md) 를 보세요.

### 5.1 부서

`관리 > 부서`

- 부서명, **전산팀** 여부, **사용** 여부를 관리합니다. `전산팀`은 IT 담당 부서 표시입니다(새 회사의 기본 `전산팀` 부서가 이것). 프로세스의 처리자 판정은 부서가 아니라 롤로 합니다.
- 사용자나 서비스가 연결된 부서는 삭제할 수 없으니 `사용` 체크를 해제하세요.

### 5.2 사용자

`관리 > 사용자`

- 검색: ID, 이름, 이메일. `사용자 등록`으로 새로 만듭니다. 목록의 롤 배지는 롤마다 색이 다르고(시스템관리자 빨강, 전산팀 파랑, 현업 전산담당 청록, 현업 사용자 회색, 회사 전용 롤은 회색), `미사용` 사용자의 행은 흐리게 표시됩니다.
- 입력 항목: 로그인 ID(영문/숫자/`._@-`, 2~64자), 이름, 이메일, 부서, **롤**(복수 선택 가능), 언어, **초기 비밀번호**(정책: 8자 이상, 영문+숫자).
- 수정 화면에서 이름, 이메일, 부서, 롤, 언어, 사용 여부를 바꾸고 `비밀번호 재설정`을 할 수 있습니다. 로그인 ID 는 등록 후 바꿀 수 없습니다. 비활성(미사용) 사용자는 로그인할 수 없고 처리자가 되지 못합니다.
- 안전장치: 자신의 시스템관리자 권한은 해제하거나 비활성화할 수 없고, **마지막 시스템관리자**도 해제·비활성화할 수 없습니다.
- 퇴사자는 삭제하지 말고 `미사용` 으로 바꾸세요(이력 보존).
- **롤 부여 기준**: 요청하는 사람은 `현업 사용자`, 현업 부서의 IT 담당(승인 담당)은 `현업 전산담당`(반드시 **부서 지정**), 전산팀원은 `전산팀`, 설정을 하는 사람은 `시스템관리자`.

### 5.3 롤/권한

`관리 > 롤/권한`

- 롤 이름(언어별)과 **롤별 권한 표**(체크)를 편집합니다. 권한은 `요청`, `처리·작업`, `리포트`, `관리`, `기타` 그룹으로 묶어 보여 주며, 열 제목(롤 이름 아래 롤 코드)이 고정되어 스크롤해도 보입니다. 시스템관리자 롤은 모든 권한을 가지며 바꿀 수 없습니다.
- `롤 추가`로 회사 전용 롤을 만들 수 있습니다(코드는 영문 대문자/숫자/`_` 2~30자). 기본 4개 롤과 사용자가 있는 롤은 삭제할 수 없습니다.
- 권한: 요청 등록, 본인 건 조회, 주관부서 건 조회, 전체 건 조회, 참조 건 조회, 단계 처리, 일정 변경 제안/합의, 리포트 조회, 프로세스 마스터 수정, 공통코드 관리, 서비스 관리, 사용자/롤/권한 관리, **작업일지 등록·관리**, **요청 분할·담당자 지정**(마지막 둘의 기본값은 전산팀·시스템관리자).
- 권한을 해제하면 바로 적용됩니다. 예를 들어 `요청 분할·담당자 지정`을 해제하면 `SR 분할` 카드와 `IT 담당자` 지정이 사라지고, `작업일지 등록·관리`를 해제하면 `작업일지` 메뉴가 사라집니다.

### 5.4 공통코드

`관리 > 공통코드`

- 코드 그룹별로 코드를 추가/수정(이름, 정렬, 사용 여부)합니다. 그룹 기본값: `유지보수 타입`(MAINT_TYPE), `우선순위`(PRIORITY), `일정변경 사유`(SCHEDULE_REASON), `서비스구분`(SERVICE_GROUP).
- 이름은 언어별로 입력할 수 있고, 비워 두면 한국어 이름이 표시됩니다. 새 코드의 정렬 기본값은 마지막 정렬값+1 입니다.
- 작업일지용 코드: 유지보수 타입 `기타작업`(`WORKLOG`)은 코드값을 바꾸거나 삭제할 수 없고 이름·정렬·사용 여부만 수정할 수 있습니다. 사용 해제해도 작업일지 등록·조회와 리포트 필터는 정상이고, 일반 요청 등록 화면에는 원래 나오지 않습니다. `접수 채널`(`CONTACT_CHANNEL`) 그룹은 작업일지를 처음 사용할 때 만들어집니다.
- **유지보수 타입을 새로 추가하면 반드시 §5.7 매핑에서 프로세스를 연결**하세요. 연결이 없으면 현업이 그 타입으로 요청을 등록할 수 없습니다.

### 5.5 서비스

`관리 > 서비스`

- 서비스 코드(영문/숫자/`_-` 2~30자), 서비스명(언어별), **현업 주관부서**, **현업 IT 담당자**, **전산 담당자**, 사용 여부를 등록합니다.
- **주관부서**는 주관부서 조회·리포트 범위와 현업 IT 담당자 후보(이 부서 소속의 현업 전산담당 롤 사용자)를 정합니다. **현업 IT 담당자**는 주관부서 후보 중에서 체크해 여러 명 지정할 수 있고 승인·사후합의 단계의 처리자가 됩니다(주관부서를 바꾸면 다른 부서 지정자는 해제됩니다). 지정하지 않거나 지정자가 모두 비활성·롤 상실·부서 이동으로 자격을 잃으면 주관부서의 현업 전산담당 전원이 처리합니다. 서비스 목록에서 `미지정`과 `지정자 확인 필요` 표시로 점검합니다.
- **전산 담당자**는 수행 단계의 처리자이며 담당자별 부하·리포트의 기준입니다. 주관부서와 전산 담당자는 정확히 지정하세요.

### 5.6 프로세스 관리

`관리 > 프로세스 관리`

프로세스는 **프로세스 마스터 → 버전 → 단계** 구조입니다. 기본으로 `일반 유지보수`(6단계)와 `긴급 장애`(5단계)가 들어 있습니다.

작업일지 전용 `기타작업일지`(`WORKLOG`) 프로세스(접수→작업완료 2단계, 승인 없음)는 **시스템 기본 프로세스**로, 처음 작업일지를 쓸 때 만들어집니다. 목록과 상세에 `시스템 기본` 배지와 안내가 표시되고, 기본 설정값이므로 **새 버전 만들기, 종료, 단계 변경, 삭제는 할 수 없습니다**(버튼이 없고 직접 요청해도 거부됩니다). 이름과 설명의 언어별 번역만 수정할 수 있습니다. 작업완료 단계의 처리자는 전산팀 전원이 아니라 작업일지를 등록한 **담당자 한 명**으로 표시됩니다(접수 단계는 요청자). 서비스×타입 매핑 표에는 나오지 않습니다.

**새 프로세스**: `프로세스 등록`에서 코드(영문 대문자/숫자/`_`), 이름, 설명을 입력하고 버전을 만들어 단계를 채운 뒤 활성화합니다.

**버전 규칙**

1. **활성/종료 버전은 수정할 수 없습니다.** `새 버전 만들기`로 초안(빈 버전 또는 기존 버전 복제)을 만들어 편집한 뒤 `활성화`합니다.
2. 활성화하면 신규 접수 건부터 새 버전을 따릅니다. 이미 진행 중인 건은 **접수 시점의 버전**대로 끝까지 진행되고 이전 실적도 그대로 보존됩니다. 진행 중인 건을 새 버전으로 옮기는 기능은 없습니다(취소 후 재등록).
3. 적용 시작일과 종료일(비우면 무기한)로 유효기간을 줄 수 있습니다. 같은 프로세스에서 유효기간이 겹치는 활성 버전은 둘 수 없습니다. 종료일 없는 새 버전을 활성화하면 앞선 활성 버전은 시작일 전날로 자동 종료됩니다.
4. 사용한 이력이 있는 버전은 삭제할 수 없고 `종료`만 가능합니다. 서비스×타입에 매핑된 프로세스는 삭제할 수 없습니다.

**단계 편집(초안 버전)**

| 항목 | 설명 |
|---|---|
| 단계명(언어별) | 화면에 보이는 이름 |
| 단계 유형 | 요청 제출 / 검토 / 합의 / 결재 / 수행 / 검수 / 종료. 첫 단계는 `요청 제출`(처리자=요청자), 마지막 단계는 `종료` |
| 처리자 유형 | 롤 / 지정 사용자 / 요청자 / 서비스 전산 담당자 / 서비스 현업 IT 담당자(기본, 미지정 시 주관부서 전원) / 서비스 현업 주관부서(주관부서 현업 전산담당 항상 전원) |
| 승인 방식 | `1명 처리 시 완료` / `전원 처리 시 완료` |
| 반려 허용, 반려 시 이동 단계 | 반려 시 돌아갈 앞선 단계(비우면 요청자에게 반환) |
| 표준 기한(영업일) | 단계 시작 후 처리 기한. 임박·초과 독촉에 사용 |
| 메일 템플릿 코드 | 이 단계 처리 요청 메일에 쓸 템플릿(비우면 기본 `STEP_ACTIVE`) |
| 첨부 | 불가 / 선택 / 필수, 최대 파일 수, 파일당 최대 MB, 허용 확장자(실행형 확장자는 허용 불가) |
| 참조자 | 롤/사용자/부서/요청자/서비스 담당자 중에서 지정. 메일 옵션: 메일 없음 / 단계 시작 시 / 단계 완료 시 / 시작·완료 모두 |

- 단계는 **드래그로 순서를 바꿉니다**(왼쪽 손잡이).
- 사용자를 고르는 목록(처리자 사용자, 참조자 사용자)은 부서별로 묶여 보이며, 목록 위 입력칸에 이름, ID, 부서명 일부를 입력하면 해당하는 사용자만 남습니다. 서비스 등록의 전산 담당자 선택도 같습니다.
- 활성화하려면 검증을 통과해야 합니다: 단계 2개 이상, 첫 단계는 요청 제출, 마지막 단계는 종료, 모든 단계의 처리자 유효, 반려 이동 단계가 앞선 단계, 유효기간 겹침 없음. 문제가 있으면 화면에 항목별로 표시됩니다.
- **참조자**는 처리 의무가 없으며 요청을 읽기 전용으로 볼 수 있습니다(참조 탭). 참조자가 그 단계의 처리자와 같은 사람이면 처리자 메일 1통만 갑니다.
- 프로세스 설정은 **`프로세스 마스터 수정` 권한(기본: 시스템관리자)이 있는 사람만** 할 수 있습니다.

### 5.7 서비스 × 타입 매핑

`관리 > 서비스×타입 매핑`

서비스(행)와 유지보수 타입(열) 표에서 칸마다 적용할 프로세스를 선택해 저장합니다. 빈 칸은 매핑 없음(해당 조합으로는 요청 등록 불가)입니다. 변경은 신규 접수 건부터 적용됩니다. 예: 모든 서비스의 `장애처리`는 `긴급 장애`, 나머지는 `일반 유지보수`.

### 5.8 메일 템플릿과 발송 이력

`관리 > 메일 템플릿`

- 기본 제공 템플릿(처리 요청, 반려/보완, 참조 안내, 일정 변경 제안/반려/대안, 기한 임박/초과, 일정 회신 독촉, SR 분할 안내 `SR_SPLIT`)을 **언어별 제목·본문**(텍스트)으로 편집합니다. 모든 언어의 제목·본문을 비워서는 저장할 수 없고, `기본값으로 되돌리기`로 복원할 수 있습니다. 사용자 정의 템플릿은 추가·삭제할 수 있으나 단계에서 쓰는 템플릿은 삭제할 수 없습니다.
- 본문에는 `{request_no}`, `{title}`, `{step}`, `{link}` 같은 **변수**를 쓸 수 있습니다(화면 아래 목록 참조). 메일은 받는 사람의 언어 설정에 맞는 템플릿으로 갑니다.

`관리 > 메일 발송 이력`

- 대기/발송 중/발송 완료/실패 상태와 시도 횟수, 다음 시도 시각, 오류 내용을 봅니다. 상단에 **발송 방식**(SMTP/파일 저장(개발용)/발송 보류)이 표시됩니다. `발송 보류`이면 메일이 대기열에만 쌓이므로 서버 `.env` 의 SMTP 설정이 필요합니다.
- 실패한 건은 행 전체가 옅은 빨간 배경으로 표시되고 `다시 보내기`로 대기열에 다시 넣습니다(자동 재시도는 5/15/60/240분 후 최대 5회). 실패 상태가 아닌 건은 다시 보낼 수 없습니다.

### 5.9 운영 점검(서버 담당자 협업)

서버 담당자가 `bin/doctor.php`, 백업(`bin/backup.php`), 주기 작업(`bin/cron.php`)을 운영합니다. 자세한 내용은 [설치운영가이드.md](설치운영가이드.md) 를 보세요. 관리자는 정기적으로 `메일 발송 이력`의 실패 건과 지연 건(대시보드)을 확인하는 것이 좋습니다.

## 6. 자주 묻는 질문

| 질문 | 답 |
|---|---|
| 요청 등록 화면에서 `매핑된 프로세스가 없습니다`라고 나옵니다 | 그 서비스와 타입 조합에 프로세스가 연결되지 않았습니다. 관리자에게 `서비스×타입 매핑`을 요청하세요. |
| `... 단계를 처리할 사용자가 없습니다`라고 나오며 제출이 안 됩니다 | 그 단계의 처리자가 될 활성 사용자가 없습니다(예: 서비스에 전산 담당자나 주관부서가 없거나 해당 롤 사용자가 없음). 관리자에게 서비스/사용자 설정을 요청하세요. |
| 내 차례인데 처리 버튼이 없습니다 | `일정 협의 중`이면 협의가 끝나야 합니다. 아니면 이미 내가 이번 회차에 처리했거나 내가 처리자가 아닙니다. |
| 메일이 오지 않습니다 | 이메일 주소(`내 정보`), 스팸함을 확인하고, 관리자는 `메일 발송 이력`의 상태·발송 방식을 확인합니다. 내가 직접 한 처리와 일정 합의는 메일이 가지 않습니다. |
| 완료요구일을 바꾸고 싶습니다 | 요청자가 직접 바꿀 수 없습니다. 작업자가 일정 변경을 제안하고 요청자가 합의하는 방식입니다. 요청 내용을 크게 바꿔야 하면 취소 후 다시 등록하세요. |
| 첨부가 안 올라갑니다 | 해당 단계가 첨부 불가이거나 파일 크기/개수/확장자 제한을 넘었습니다. 안내 문구의 제한 값을 확인하세요. |
| 다른 회사 요청이 보이지 않습니다 | 정상입니다. 회사별로 데이터가 완전히 분리되어 있습니다. |
| 남의 요청 주소를 열었더니 `404` 가 나옵니다 | 정상입니다. 열람 권한이 없는 요청은 존재 여부를 숨기기 위해 403 이 아니라 404 로 응답합니다. 관리 화면은 권한이 없으면 403 입니다. |
| `SR 분할` 카드나 `IT 담당자` 지정이 안 보입니다 | `요청 분할·담당자 지정` 권한이 있는 계정(전산팀, 시스템관리자)에게만 보이며, 진행 중인 일반 요청의 현재 단계가 검토·합의·승인·수행이고 일정 협의 중이 아닐 때만 분할할 수 있습니다. |
| 작업일지를 잘못 등록했습니다 | 등록한 본인이나 시스템관리자가 `작업일지` 목록에서 수정·삭제합니다(삭제하면 첨부까지 지워지고 복구되지 않습니다). 다른 전산팀원은 볼 수만 있습니다. |
| 서버 두 대(다른 포트)를 띄웠더니 로그인이 풀립니다 | 브라우저 쿠키는 포트를 구분하지 않아 세션이 섞입니다. 개발·검증 시에는 서버를 한 대만 쓰거나 호스트 이름(`127.0.0.1` 과 `localhost`)을 다르게 접속하세요. |

## 7. 용어

| 용어 | 뜻 |
|---|---|
| 서비스 | 유지보수 관리 대상 시스템(예: ERP, 인사시스템) |
| 유지보수 타입 | 신규개발, 기능수정, 장애처리, 데이터작업, 기타 |
| 프로세스 | 타입별로 정의된 단계(접수→검토→승인→수행→검수→종료 등) |
| 완료요구일 | 요청자가 요구하는 완료 일정(필수) |
| 합의 완료일(계획) | 일정 변경이 합의되어 확정된 완료일 |
| 처리함 | 내가 지금 처리해야 하는 요청 모음 |
| 참조자 | 처리 의무 없이 읽기 전용으로 보거나 안내 메일만 받는 사람 |
| 투입시간 | 작업에 들인 시간(시간 단위로 입력·집계, MD 환산 없음) |
