# SRMS 신규 회사 초기 설치 가이드

SRMS 를 **다른 회사(고객사 또는 그룹사)에 처음 도입할 때**의 전체 절차입니다. 준비 → 배포 패키지 → 서버 설치 → 초기 데이터 구성 → 검증 → 인계 순서로 진행합니다. 서버 설정의 세부 값은 [설치운영가이드.md](설치운영가이드.md), 설정 화면 사용법은 [사용자매뉴얼.md](사용자매뉴얼.md) §5, 검증 시나리오는 [테스트시나리오.md](테스트시나리오.md) 를 함께 봅니다.

## 1. 설치 방식 선택

| 구분 | A. 회사 전용 서버(권장) | B. 기존 서버에 회사 추가(그룹사) |
|---|---|---|
| 상황 | 별개의 회사에 납품하거나 데이터를 물리적으로 분리해야 함 | 이미 운영 중인 SRMS 를 그룹사가 함께 사용 |
| 방법 | 새 서버에 설치하고 `SINGLE_COMPANY` 로 단일 회사 모드로 운영 | 기존 서버에서 `bin/company.php add` 실행 |
| 데이터 분리 | 서버·DB 파일 자체가 분리 | 같은 DB 파일 안에서 회사코드로 논리 분리(앱이 강제) |
| 로그인 화면 | 회사 선택이 없음 | 활성 회사 목록에서 회사를 선택. **다른 회사 이름이 로그인 화면에 보임** |
| 공유되는 것 | 없음 | `.env`(SMTP, 인증 방식, 언어 목록), 코드 버전, 서버 자원, 백업 일정 |
| 장애 영향 | 회사별 독립 | 서버 장애·업그레이드가 모든 회사에 영향 |

그룹사 간 공유가 필요 없고 회사 이름이 서로 노출되면 안 된다면 **A 방식**을 선택하세요. B 방식은 §9 를 보세요.

## 2. 사전 준비(고객사에서 받을 것)

### 2.1 인프라

- [ ] 서버(OS 무관). PHP 8.5.x, 확장 `pdo_sqlite`, `sqlite3`, `mbstring`, `fileinfo`, `openssl`, `ctype`, `filter`, `hash`(선택 `intl`). SQLite 는 PHP 에 포함된 3.35 이상
- [ ] 웹서버: Apache 2.4 또는 Nginx(+PHP-FPM). 설정 샘플은 [deploy/](../deploy)
- [ ] 접속 주소(도메인)와 HTTPS 인증서
- [ ] 사내 SMTP 서버 정보(주소, 포트, 인증 계정/비밀번호, 암호화 방식, 발신 주소). 서버에서 SMTP 서버로 접속할 수 있도록 방화벽 허용
- [ ] 서버의 디스크 용량(DB·첨부·백업 증가분)과 백업을 복사해 둘 다른 디스크/서버
- [ ] 서버 운영 담당자(PHP/웹서버/백업), SRMS 관리자(시스템관리자 롤)

### 2.2 업무 정보

- [ ] 회사 코드(영문/숫자/`_-` 20자 이하, 예 `ACME`)와 회사명, 기본 언어(ko/ja/en/zh)
- [ ] 조직(부서 목록)과 **전산팀 부서**
- [ ] 사용자 목록: 로그인 ID(사번 권장), 이름, 이메일, 부서, 롤(현업 사용자 / 현업 전산담당 / 전산팀 / 시스템관리자)
- [ ] 서비스(관리 대상 시스템) 목록: 서비스 코드/이름, **현업 주관부서**, **현업 IT 담당자**(주관부서 소속 현업 전산담당 중 승인할 사람), **전산 담당자**
- [ ] 유지보수 타입(기본: 신규개발, 기능수정, 장애처리, 데이터작업, 기타)과 서비스×타입별로 쓸 프로세스
- [ ] 프로세스 요구: 기본 `일반 유지보수`(접수→검토→승인→수행→검수→종료; 승인은 서비스에 지정된 현업 IT 담당자)와 `긴급 장애`(접수→승인→수행→사후합의→종료)를 그대로 쓸지, 단계·처리자·기한·첨부 규칙·참조자 변경이 필요한지
- [ ] 사용할 언어와 메일 문구 가이드(회사명, 문의처)
- [ ] 인증 방식: 로컬 로그인만 / SSO 연동(SSO 문서·라이브러리 제공 가능한 시점 확인)
- [ ] 보안 요구: HTTPS 필수 여부, 비밀번호 정책 예외, 접근 가능 네트워크 범위

> 서비스의 **주관부서와 전산 담당자**(권장: **현업 IT 담당자**도), 부서별 **현업 전산담당** 사용자가 비어 있으면 프로세스가 진행되지 않습니다(승인·수행 단계의 처리자가 없어 제출이 거부됩니다). 사용자 목록을 받을 때 반드시 같이 정리하세요.

## 3. 배포 패키지 만들기

저장소(`c:\dev\srms`)에서 고객사에 보낼 파일을 모읍니다. 배포용 빌드 스크립트는 없으므로 폴더를 복사하되 아래를 지켜 주세요.

| 포함 | 제외 |
|---|---|
| `public/`, `app/`, `database/`, `bin/`, `deploy/`, `vendor/`, `docs/` | `.tools/`(개발용 휴대 PHP) |
| `storage/` 의 **빈 폴더 구조**(`db`, `attachments`, `logs`, `backup`, `mail`) | `storage/` 안의 개발 DB, 첨부, 로그, 백업, 메일 파일(`*.sqlite*`, `storage/cron.lock` 포함) |
| `.env.example` | `.env`(개발 설정·비밀번호가 들어 있음) |
| `docs/` 의 운영 문서와 필요 시 `설계서.md`, `개발관리.md` | `tests/`, `tools/`(개발·검증용. 유지보수 계약상 필요하면 별도 전달), `bin/demo.php`(운영에서는 어차피 실행 거부) |

- **절대 개발 DB 를 그대로 보내지 마세요.** 개발·데모 계정(`admin/Admin1234`, `Demo1234` 등)과 샘플 데이터가 들어 있습니다. 고객사 DB 는 항상 `bin/install.php` 로 새로 만듭니다.
- 보내기 전에 현재 코드로 자동 테스트(214건)와 문법 검사를 통과했는지 확인하고 버전(날짜 또는 태그)을 기록합니다.
- 번들 라이브러리(PHPMailer, Bootstrap, Quill 등)와 라이선스는 [THIRD_PARTY.md](THIRD_PARTY.md) 에 있고 이 파일도 포함합니다.

## 4. 서버 설치

아래는 [설치운영가이드.md](설치운영가이드.md) §3~§8 을 이 도입 작업에 맞게 정리한 순서입니다. 경로는 `/srv/srms` 로 예를 듭니다.

1. **파일 배치**: 패키지를 서버에 풀고 웹서버 루트를 `public/` 으로 지정합니다.
   - Nginx: [deploy/nginx.conf.sample](../deploy/nginx.conf.sample), Apache: [deploy/apache.conf.sample](../deploy/apache.conf.sample). 존재하지 않는 경로는 `index.php` 로 넘어가야 합니다(`try_files` / `FallbackResource`).
   - `app/`, `storage/`, `database/`, `.env` 가 URL 로 열리면 안 됩니다.
2. **PHP 설정**: [deploy/php.ini.sample](../deploy/php.ini.sample) 의 값을 적용합니다(`expose_php=Off`, `display_errors=Off`, 업로드 한도 20MB/요청당 64MB 등). 웹서버의 본문 크기 제한도 맞춥니다.
3. **권한**: `storage/` 에 PHP 실행 사용자의 쓰기 권한을 줍니다. `.env` 는 PHP 실행 사용자만 읽도록 제한합니다.
4. **`.env` 작성**: `.env.example` 을 `.env` 로 복사해 입력합니다. 회사 전용 서버(A 방식) 권장값:

   ```ini
   APP_ENV=production
   APP_URL=https://srms.고객사도메인
   APP_TZ=Asia/Seoul
   DB_PATH=storage/db/srms.sqlite
   STORAGE_PATH=storage
   DEFAULT_LANG=ko
   ENABLED_LANGS=ko,en            # 쓸 언어만(ko,ja,en,zh 중)
   AUTH_MODE=LOCAL                # SSO 연동 후 BOTH 로 변경
   SINGLE_COMPANY=ACME            # 단일 회사 모드: 회사 코드와 같게
   SESSION_LIFETIME_MIN=30
   SMTP_HOST=smtp.고객사.com
   SMTP_PORT=587
   SMTP_USER=...
   SMTP_PASS=...
   SMTP_SECURE=tls
   MAIL_FROM=srms@고객사.com
   MAIL_FROM_NAME=SRMS
   MAIL_DRIVER=smtp
   BACKUP_KEEP_DAYS=14
   ```

   - 하위 경로로 배포하면 `APP_BASE_PATH=/srms`, 리버스 프록시 뒤에서 HTTPS 를 종료하면 `TRUST_PROXY=1`.
   - DB·첨부·백업은 **웹루트 밖**이어야 하고, 용량이 큰 디스크를 쓰려면 `DB_PATH`/`STORAGE_PATH`/`BACKUP_PATH` 를 그 경로로 지정합니다.
5. **최초 설치**: 스키마 생성, 기본 롤·권한·공통코드·기본 프로세스·메일 템플릿(ko/ja/en/zh)·번역을 시드하고 첫 회사와 시스템관리자를 만듭니다.

   ```
   php bin/install.php --company=ACME --company-name="주식회사 ACME" --lang=ko \
       --admin=sysadmin --admin-name="시스템관리자" --admin-email=sysadmin@고객사.com
   ```

   `--password` 를 생략하면 **임시 비밀번호가 한 번 출력**되므로 안전하게 전달하세요. 입력할 때는 8자 이상, 영문+숫자여야 합니다. 이 명령은 같은 회사 코드가 이미 있으면 거부합니다.
6. **점검**: `php bin/doctor.php` 를 실행해 `[FAIL]` 이 없게 합니다. 이 시점의 `[WARN]` 은 대개 SMTP 미설정, 주기 작업/백업 미실행, HTTPS 아님 같은 후속 항목입니다.
7. **SMTP 테스트**: `php bin/mailtest.php 받는사람@고객사.com` 으로 메일이 실제 도착하는지 확인합니다. 실패하면 SMTP 정보·방화벽·인증서를 점검합니다.
8. **주기 작업 등록**: [deploy/schedule.sample.txt](../deploy/schedule.sample.txt) 를 참고해 `php bin/cron.php`(1시간마다)와 `php bin/backup.php`(매일 02:30)를 등록합니다. Windows 는 작업 스케줄러, Linux 는 crontab 입니다.
9. **웹 접속**: `https://srms.고객사도메인` 으로 접속해 관리자로 로그인하고 **임시 비밀번호를 바로 변경**합니다(이름 메뉴 > 내 정보).

### 설치 직후 자동으로 만들어지는 데이터

| 구분 | 내용 |
|---|---|
| 롤 | 현업 사용자 `REQUESTER`, 현업 전산담당 `BIZ_IT`, 전산팀 `IT_TEAM`, 시스템관리자 `SYS_ADMIN` 과 각 권한 |
| 부서 | `전산팀`(전산팀 표시) 1개 |
| 공통코드 | 유지보수 타입(NEW_DEV/MODIFY/BUGFIX/DATA/ETC), 우선순위(LOW/NORMAL/HIGH/URGENT), 일정변경 사유(7종), 서비스구분(빈 그룹) |
| 프로세스 | `일반 유지보수`(6단계), `긴급 장애`(5단계) — 각각 v1 활성. 작업일지를 처음 쓰면 시스템 기본 프로세스 `기타작업일지`(변경·삭제 불가)가 추가됩니다 |
| 메일 템플릿 | 기본 11종(SR_SPLIT 포함) × 언어 |
| 사용자 | 시스템관리자 1명(전산팀 부서) |
| 서비스/매핑 | **없음** → §5 에서 설정해야 요청을 받을 수 있음 |

## 5. 초기 데이터 구성(시스템관리자 화면)

관리자로 로그인해 아래 순서로 설정합니다. 화면 사용법은 [사용자매뉴얼.md](사용자매뉴얼.md) §5 를 보세요. 의존 관계 때문에 **순서를 지키는 것**이 중요합니다.

| 순서 | 메뉴 | 할 일 | 확인 |
|---|---|---|---|
| 1 | `관리 > 부서` | 고객사 조직의 부서를 등록하고, IT 담당 부서는 `전산팀` 체크 | 서비스 주관부서·사용자 소속으로 선택 가능 |
| 2 | `관리 > 사용자` | 전체 사용자 등록: **현업 사용자**, **현업 전산담당**(반드시 소속 부서 지정), **전산팀**, 필요 시 추가 시스템관리자 | 각 계정 로그인 가능. 퇴사·미사용자는 `사용` 해제 |
| 3 | `관리 > 서비스` | 관리 대상 시스템을 등록하고 **현업 주관부서**, **현업 IT 담당자**(주관부서 선택 후 그 부서의 현업 전산담당 중 체크), **전산 담당자** 지정 | 서비스 목록의 `현업 IT 담당자` 칸에 `미지정`·`지정자 확인 필요` 표시가 없음 |
| 4 | `관리 > 공통코드` | 고객사 용어에 맞게 타입·우선순위·사유를 조정(추가/이름 변경/사용 해제), 언어별 이름 입력 | 요청 등록 화면 목록에 반영 |
| 5 | `관리 > 프로세스 관리` | 고객사 요구에 맞게 프로세스를 조정. 활성 버전은 수정할 수 없으므로 **새 버전을 복제해 편집 후 활성화** | 활성화 검증 통과, 프로세스 흐름 미리보기 |
| 6 | `관리 > 서비스×타입 매핑` | 모든 (서비스, 타입) 조합에 프로세스를 연결 | 요청 등록에서 조합 선택 시 흐름이 표시됨 |
| 7 | `관리 > 롤/권한` | 고객사 정책에 맞게 롤별 권한 조정(필요할 때만), 회사 전용 롤 추가 | 롤별 메뉴/조회 범위 확인 |
| 8 | `관리 > 메일 템플릿` | 회사명·문의처를 넣어 문구를 다듬고, 쓰는 언어 모두 제목·본문 입력 | 테스트 요청으로 메일 확인 |
| 9 | `관리 > 메일 발송 이력` | 발송 방식이 `SMTP` 인지 확인 | 상단 표시가 SMTP |

### 구성 시 규칙과 주의

- **현업 전산담당**은 부서가 있어야 합니다. 승인 단계(`서비스 현업 IT 담당자`; 긴급 프로세스는 사후합의)는 서비스에 지정된 현업 IT 담당자(여러 명 가능)가 처리하고, 지정이 없거나 지정자가 모두 자격(활성·`BIZ_IT` 롤·주관부서 소속)을 잃으면 주관부서의 `BIZ_IT` 활성 사용자 전원이 처리합니다. 현업 부서가 크면 서비스마다 담당자를 지정해 두세요(`bin/doctor.php` 이 지정자가 없는 서비스를 경고합니다).
- 수행 단계(`서비스 전산 담당자`)는 **서비스에 지정된 전산 담당자 한 명(서비스당)**만 처리하므로, 휴가·퇴사로 비면 요청이 멈춥니다. 서비스 담당자는 처리 시점에 확인하므로 담당자를 바꾸면 진행 중인 요청의 수행 단계 처리자도 새 담당자로 바뀝니다. 담당자 부재 시 대체 지정 방법을 정해 두세요.
- 검토·종료는 `전산팀` **롤** 전체가 처리자입니다. 전산팀 인원 모두에게 롤을 주세요.
- 새 유지보수 타입을 만들면 **반드시 매핑**하세요.
- 프로세스는 변경 후 새로 접수되는 건부터 적용됩니다. 이미 진행 중인 건은 이전 버전을 따릅니다.
- 관리자가 새로 입력한 이름(서비스, 코드, 프로세스, 단계)은 언어별 번역을 넣지 않으면 한국어로 표시됩니다. 영어/일본어/중국어를 쓰는 고객사는 번역도 입력하세요.
- 사용자 일괄 등록 기능은 없습니다. 수십 명 이상이면 [bin/demo.php](../bin/demo.php) 의 `Users::create` 호출 방식을 참고해 일회성 스크립트를 만들어 실행합니다(스크립트는 `Migrator::run()` 후 `Scope::set('회사코드')` 를 설정해야 하며, 사용 후 서버에서 삭제하세요).

## 6. 인증(SSO) 연동

초기 오픈은 `AUTH_MODE=LOCAL` 로 시작하고, SSO 문서·라이브러리를 받으면 연동합니다. 절차는 [설치운영가이드.md](설치운영가이드.md) §9 를 따릅니다. 연동 시 사번은 `user.login_id` 와 같게 등록해 두어야 합니다. 운영 초기에는 SSO 장애 대비로 `AUTH_MODE=BOTH` 를 권장합니다. SSO 전용(`SSO`)으로 바꾸기 전에 관리자 계정으로 로컬 로그인이 가능한지 확인하세요.

## 7. 오픈 전 검증

1. **서버 점검**: `php bin/doctor.php` 가 `[FAIL]` 없이 통과하고, `[WARN]` 항목은 사유를 정리합니다. 보안 점검표는 [설치운영가이드.md](설치운영가이드.md) §11 입니다.
2. **시나리오 수행**: [테스트시나리오.md](테스트시나리오.md) 를 이 회사의 실제 서비스·계정으로 수행합니다. 필수 최소 범위:
   - `COM-01`, `COM-06`~`COM-09`
   - `REQ-03`~`REQ-09`, `E2E-01`~`E2E-09`(일반 프로세스 끝까지)
   - `E2E-10`~`E2E-13`(반려·보완), `E2E-14`~`E2E-19`(일정 협의)
   - `SEC-01`~`SEC-03`, `SEC-12`, `OPS-03`(SMTP), `OPS-06`~`OPS-07`(백업·복원), `OPS-09`(웹서버 설정)
3. **테스트 데이터 정리**: 검증용으로 만든 요청은 취소 처리하고 검증용 계정은 `사용` 을 해제합니다. 요청번호와 이력은 삭제되지 않고 남으므로, 정식 오픈 전에 정리가 필요하면 **새 DB 로 재설치**(§4 5번부터 다시)하는 편이 깔끔합니다. 이 경우 기존 DB·첨부·백업 파일을 안전하게 보관하거나 삭제하세요.
4. **백업 복원 연습**을 1회 수행하고 소요 시간을 기록합니다.

## 9. 기존 서버에 회사 추가(B 방식)

이미 운영 중인 서버에 그룹사를 추가할 때입니다. 코드·`.env` 는 그대로 두고 회사 데이터만 추가합니다.

1. **백업**: `php bin/backup.php`
2. **회사 생성**:

   ```
   php bin/company.php add A01 "A 계열사" --admin=a01admin --admin-name="A사 관리자" \
       --admin-email=admin@a01.com --lang=ko
   php bin/company.php list
   ```

   회사 코드는 영문/숫자/`_-` 20자 이하이며 이미 있으면 거부됩니다. `--password` 를 생략하면 임시 비밀번호가 출력됩니다. 회사마다 롤·권한·공통코드·`전산팀` 부서·기본 프로세스·메일 템플릿·번역이 **독립적으로 시드**되고 첫 시스템관리자가 만들어집니다.
3. **로그인 확인**: 로그인 화면의 회사 목록에 새 회사가 나타나고, 새 관리자로 로그인하면 빈 상태(기본 시드만)여야 합니다. 다른 회사 데이터는 보이지 않아야 합니다.
4. **초기 구성**: §5 의 순서대로 그 회사 관리자가 설정합니다.
5. **공유 설정 확인**: 메일 발신 주소·SMTP·`ENABLED_LANGS`·`AUTH_MODE` 는 서버 전체 값입니다. 회사별로 다르게 둘 수 없으니 회사 간 합의가 필요합니다. 회사의 기본 언어는 `--lang` 값입니다.
6. **검증**: [테스트시나리오.md](테스트시나리오.md) 의 `SEC-05`(회사 격리)를 두 회사 계정으로 수행합니다.

유의: 회사 비활성화·삭제용 명령/화면은 없습니다(활성 회사는 로그인 화면에 항상 나타남). 회사 간 통합 조회 화면도 없습니다. 이 기능이 필요하면 별도 개발이 필요합니다.

## 10. 업그레이드와 재설치

- 같은 서버의 코드 업그레이드: `php bin/backup.php` → 파일 교체(`.env`, `storage/` 는 유지) → `php bin/migrate.php` → `php bin/doctor.php`. `migrate` 는 새 스키마를 적용하고 **모든 회사**에 새 기본 데이터를 보강합니다(새 권한 코드는 추가되지만 기존 롤에 자동 부여되지는 않으므로 필요하면 `관리 > 롤/권한` 에서 켭니다). 011 마이그레이션은 기존 투입공수(`effort_md`) 값을 옮기지 않고 버리므로(시간 `effort_hours` 로 대체) 011 이전 버전에서 올릴 때는 반드시 백업하고 필요한 값을 별도로 보관하세요. 012 마이그레이션은 서비스별 현업 IT 담당자 테이블을 추가하고, 기존 회사의 기본 프로세스(`일반 유지보수` 승인, `긴급 장애` 사후합의)의 처리자 유형을 `서비스 현업 IT 담당자`로 한 번 바꿉니다(담당자를 지정하기 전에는 주관부서 현업 전산담당 전원이 처리하므로 동작은 이전과 같음). 업그레이드 후 `관리 > 서비스`에서 서비스마다 현업 IT 담당자를 지정하세요(`bin/doctor.php` 가 지정자가 없는 서비스를 알려 줌).
- 처음부터 다시 설치하려면 서버의 DB 파일(`DB_PATH`)과 `-wal`, `-shm` 파일, `storage/attachments/` 를 안전하게 이동(또는 삭제)한 뒤 §4 의 5번 `bin/install.php` 부터 다시 수행합니다. 운영 중 데이터는 먼저 백업하세요.

## 11. 설치 중 자주 만나는 문제

| 증상 | 원인과 조치 |
|---|---|
| 로그인 화면은 뜨는데 모든 화면이 404 | 웹서버가 없는 경로를 `index.php` 로 넘기지 않음. `try_files` / `FallbackResource` 설정 확인 |
| `bin/install.php` 가 `missing --...` 로 종료 | 필수 옵션(`--company`, `--company-name`, `--admin`, `--admin-name`, `--admin-email`) 누락 |
| `company already exists` | 이미 설치된 DB 에 같은 회사 코드로 다시 실행함. 의도한 새 설치면 DB 를 비우거나 다른 DB_PATH 를 사용 |
| `doctor` 의 쓰기 권한 `[FAIL]` | `storage/` 와 하위 폴더에 PHP 실행 사용자 쓰기 권한 부여 |
| `doctor` 의 SINGLE_COMPANY `[FAIL]` | `.env` 의 `SINGLE_COMPANY` 가 실제 회사 코드와 다름(대소문자 포함) |
| 로그인 화면에 회사 선택이 보임 | `SINGLE_COMPANY` 가 비어 있음. 단일 회사 서버라면 회사 코드를 입력 |
| 메일이 대기에만 쌓임 | `MAIL_DRIVER=off` 이거나 SMTP 미설정(운영 기본). `.env` 설정 후 `bin/mailtest.php`, `bin/cron.php` 로 확인 |
| 제출 시 `... 단계를 처리할 사용자가 없습니다` | 서비스의 주관부서/전산 담당자 미지정, 주관부서에 `현업 전산담당` 롤 사용자 없음, 해당 롤 사용자 없음 |
| 요청 등록 시 `매핑된 프로세스가 없습니다` | `서비스×타입 매핑` 미설정 |
| 업로드가 실패함 | `php.ini` 의 `upload_max_filesize`/`post_max_size`/웹서버 본문 크기 제한이 정책(파일당 20MB)보다 작음 |
| 링크가 잘못된 주소로 나감(메일 본문) | `APP_URL`(및 하위 경로 배포 시 `APP_BASE_PATH`)이 실제 접속 주소와 다름 |
